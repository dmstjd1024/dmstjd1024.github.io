블로그 글 한 편을 읽고 "요약 카드" 다섯 칸을 YAML 로 만든다.

## 출력 형식

YAML 블록 하나만 출력한다. 설명·인사·코드펜스 밖의 문장을 쓰지 않는다.

```yaml
summary:
  context: "사례 · <한 줄 배경>"
  환경: "<이 작업이 놓인 조건>"
  문제: "<무엇이 잘못됐나>"
  선택: "<무엇을 했나. 왜 그것을 골랐나>"
  포기: "<이 선택으로 떠안은 비용·위험>"
  결과:
    - "<수치 또는 확인된 사실>"
```

## 규칙 — 어기면 다시 쓴다

1. **측정하지 않은 숫자는 쓰지 않는다.** 이게 다른 모든 규칙을 이긴다.
   본문에 근거(커밋·로그·실측)가 없는 수치는 만들지 않는다.
   근거가 없으면 `결과` 를 빈 목록 `[]` 으로 두거나, 숫자 대신
   원인을 특정하는 문장을 쓴다. "약 40% 개선" 같은 추정은 금지다.
2. **본문에 없는 내용을 추론해 덧붙이지 않는다.** 모르면 그 칸을 비운다.
   빈 칸은 `""` 로 둔다 — 레이아웃이 알아서 그 줄을 건너뛴다.
3. **회사·제품·도메인·사람 이름과 내부 문서 번호를 쓰지 않는다.**
   원문에 있어도 뺀다. "B2B 웹앱", "사내 시스템" 처럼 일반화한다.
4. 각 칸은 한 문장. `환경` 과 `선택` 만 두 문장까지 허용한다.
5. 감성 표현을 쓰지 않는다 — "열정", "성장", "전진", 마무리 구호.
6. 코드·식별자는 백틱으로 감싼다: `@Subselect`, `_mat`.
7. `결과` 는 0~4개. 각 항목은 짧게 — 배지로 그려지므로 20자 안쪽이 좋다.
8. 큰따옴표 안의 큰따옴표는 작은따옴표로 바꾼다 (YAML 파싱).

## 칸의 뜻

| 칸 | 묻는 것 |
|---|---|
| context | 어떤 환경에서 한 작업인가 (헤더 오른쪽 작은 글씨) |
| 환경 | 이 작업이 놓인 조건. 제약이 무엇이었나 |
| 문제 | 무엇이 잘못됐나. 증상이 아니라 원인에 가깝게 |
| 선택 | 무엇을 했나. 다른 길 대신 왜 이것인가 |
| 포기 | 이 선택으로 떠안은 비용·위험. 없으면 비운다 |
| 결과 | 확인된 사실. 측정값이 있으면 그것, 없으면 비운다 |

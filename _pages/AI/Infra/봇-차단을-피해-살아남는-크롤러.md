## 문제: 반복 크롤링이 IP 차단에 걸리기 시작했다

- 골프 부킹 정보를 **10분 주기**로 크롤링하는 대시보드 운영 중
- 반복 패턴 자체가 상대 서버 입장에서는 봇으로 보이기 딱 좋은 형태
- 코드에 새로 생긴 것
  - `_direct_blocked` 플래그
  - "IP 차단 시" 분기

직접 연결 방식으로는 더 이상 안정적으로 크롤링을 지속할 수 없었다는 뜻이다.

## 설계: 프록시를 목록이 아니라 순환 상태로 다룬다

- 가장 단순한 접근 — 프록시 서버 주소 몇 개를 코드에 하드코딩
- 실제 선택 — Webshare 무료 프록시 API에서 목록을 그때그때 새로 수신
- 이유: 무료 프록시는 수명이 짧아 금방 만료. 하드코딩보다 매번 최신 목록을 받는 편이 유지보수 부담이 적다.

```python
def _fetch_webshare_proxies(api_token: str) -> List[str]:
    """Webshare API에서 프록시 목록을 가져옵니다."""
    resp = requests.get(
        "https://proxy.webshare.io/api/v2/proxy/list/?mode=direct&page=1&page_size=100",
        headers={"Authorization": f"Token {api_token}"},
        timeout=10,
    )
    ...
```

- API 하나에만 의존 시 위험 — 그 API가 실패하면 크롤러 완전 정지
- 대비책: `config.py`에 수동 입력 프록시 목록(`PROXY_LIST`) 유지 — API 실패 시 폴백 경로

핵심은 프록시를 단순한 "목록"이 아니라 **순환하는 상태**로 다룬 부분이다.

```python
def _rotate_proxy(self) -> bool:
    """다음 프록시로 전환합니다. 전환 성공 시 True, 모두 소진 시 False."""
    if not self._proxy_list:
        return False

    if self._current_proxy_index == -1:
        # 직접 연결 중이었다면 첫 프록시로
        self._current_proxy_index = 0
        self._apply_proxy(self._proxy_list[0])
        return True

    next_index = self._current_proxy_index + 1

    if next_index >= len(self._proxy_list):
        if not self._direct_blocked:
            # 프록시를 다 돌았으면 직접 연결도 한 번 시도
            self._current_proxy_index = -1
            self._clear_proxy()
            return True
        else:
            # 직접 연결도 막혔으면 처음 프록시부터 다시
            self._current_proxy_index = 0
            self._apply_proxy(self._proxy_list[0])
            return True

    self._current_proxy_index = next_index
    self._apply_proxy(self._proxy_list[next_index])
    return True
```

순환 순서:

- 직접 연결
- → 프록시 1 → 프록시 2 → … → 프록시 소진
- → (아직 안 막혔다면) 직접 연결 재시도
- → 그래도 막혔다면 처음 프록시부터 다시

프록시를 "쓰다가 버리는 자원"이 아니라, 직접 연결까지 포함한 하나의 순환 링으로 구성한 것이다.

## 프록시 전환만으로는 부족했다

프록시 교체와 별개로 붙인 것:

- HTTP 요청 실패 시 지수 백오프 재시도 — 최대 **2회** (2초 → 4초 대기)
- 프록시·IP 변경 시 세션 쿠키(JSESSIONID) 자동 초기화

## 크롤링 결과가 0건일 때를 별도로 다뤘다

문제 상황:

- 프록시가 막혀 크롤링이 빈 결과 반환
- 그게 그대로 "오늘은 매물이 없다"는 정상 데이터로 화면에 반영
- 실패와 진짜 0건을 구분하지 않으면 → 크롤러가 죽어 있어도 사용자 눈에는 "매물이 하나도 없는 날"

조치:

- 크롤링 결과 0건이면 기존 캐시·DB 데이터 덮어쓰기 금지
- stale 삭제 로직에 최소 기준 — **50건 미만이면 삭제 스킵**

크롤링이 일부만 성공했을 때, 멀쩡히 남아 있는 기존 데이터까지 "오래됐다"고 오인해서 지워버리는 걸 막기 위해서다.

## 최종 구성

- 프록시 로테이션·재시도·데이터 보호 로직을 한 번에 묶어 배포
- 크롤링 주기 **10분 → 30분** 확대 — 순환 주기 축소 자체가 차단 빈도를 낮추는 가장 근본적인 방법

```
- Webshare 무료 프록시 10개 자동 로드 (WEBSHARE_API_TOKEN)
- IP 차단 시 프록시 자동 전환 (로테이션)
- HTTP 요청 실패 시 지수 백오프 재시도 (2회, 2s→4s)
- 세션 쿠키 자동 초기화 (JSESSIONID 확보)
- 크롤링 결과 0건 시 기존 캐시/DB 데이터 보호
- stale 삭제 최소 기준 50건 미만이면 삭제 스킵
- 크롤링 주기 10분 → 30분으로 변경
```

## 남는 교훈

크롤러의 안정성은 "차단당했을 때 우회한다" 하나로 끝나지 않는다. 함께 설계해야 할 것:

- 우회 수단(프록시) 소진 시 순환 방식
- 실패와 정상적인 빈 결과의 구분
- 부분 실패가 기존 데이터를 오염시키지 않게 하는 방어

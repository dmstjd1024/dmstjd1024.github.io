## 상황: 요청 하나에 붙어 있던 것들

부하 테스트에서 TPS가 목표에 못 미쳤다. 병목이 한 곳이 아니라 인증 경로에 겹겹이 쌓여 있었다.

- 매 요청마다 감사 로그를 **동기로** DB에 INSERT
- 인증 필터와 권한 필터가 **각자** 사용자를 조회 — 같은 요청 안에서 두 번
- 권한 검사용 메뉴 목록도 매 요청 DB 조회

29분 동안 여섯 번 커밋해서 이걸 벗겨냈다. 그중 하나는 **3분 전의 내 최적화가 만든 회귀를 고치는 커밋**이다. 이 글의 중심은 그 하나다.

## ① 감사 로그를 요청 경로에서 뺐다

`@Async`를 붙여 별도 스레드로 넘겼다. 그런데 붙이자마자 사용자를 못 찾는다.

- Spring Security의 `SecurityContextHolder`는 기본이 `ThreadLocal`(스레드마다 독립된 저장소)
- `@Async` 메서드는 다른 스레드에서 돈다 → **컨텍스트가 비어 있다**
- 기존 코드는 `getLoginUser()`로 현재 사용자를 꺼내 쓰고 있었다

해결은 스레드 경계를 넘는 것을 최소화하는 쪽으로 했다.

```java
// 동기 스레드(필터)에서 미리 뽑아 인자로 넘긴다
Authentication auth = SecurityContextHolder.getContext().getAuthentication();
String username = (auth != null) ? auth.getName() : null;
auditLogService.saveAuditLog(username, ipAddress, httpStatus, reqMethod, /* ... */);
```

```java
public User findByUsernameForAudit(String username) {
    return userRepository.findWithAgencyByDelYnFalseAndUsername(username)
        .orElseGet(this::anonymousUser);
}
```

- 넘긴 것이 **엔티티가 아니라 문자열**인 게 중요하다. 엔티티를 넘기면 영속성 컨텍스트 밖에서 지연 로딩 문제가 생긴다
- `orElseGet(this::anonymousUser)` — 비인증 요청도 감사 로그는 남아야 하므로 예외 대신 익명 사용자로 대체

## ② 커넥션 풀을 늘렸다

```yaml
maximum-pool-size: 50   # 20 이었다
```

한 줄짜리 커밋이고, 제목에 **"TPS 100 달성"**이라고 적혀 있다. 이 시리즈에서 유일하게 숫자가 나오는 지점이다.

정직하게 덧붙이면 — **개선 전 수치는 어디에도 없다.** JMeter로 로컬에서 재긴 했다(저장소 `.gitignore`에 `jmeter/` 규칙이 두 달 전부터 있다). 다만 그 산출물을 형상관리에서 제외해서, 지금은 "100을 달성했다"는 커밋 제목만 남았다. 전후 비교를 증거로 쓸 수 없는 상태다.

측정은 하고 기록을 안 남기면 이렇게 된다.

## ③ 사용자 재조회를 없앴다 — 그리고 깨뜨렸다

인증 필터와 권한 필터가 같은 요청에서 같은 사용자를 두 번 조회하고 있었다. 앞에서 조회한 걸 뒤에서 쓰면 왕복 한 번이 사라진다.

```java
// 인증 필터 — 조회한 것을 넣어둔다
request.setAttribute("AUTH_USER", user);
```

```java
// 권한 필터 — 있으면 쓰고, 없으면 직접 조회 (다른 경로 대비)
User user = (User) request.getAttribute("AUTH_USER");
if (user == null) {
    user = userRepository.findUserWithRoleByUsername(username)
        .orElseThrow(() -> new BusinessLogicException(ExceptionCode.NOT_FOUND_USER));
}
```

깔끔해 보인다. **그런데 권한 검사가 깨졌다.**

### 두 필터가 서로 다른 쿼리를 쓰고 있었다

권한 검사는 사용자의 역할 목록을 본다.

```java
List<Role> roleList = user.getUserRoleList().stream()
    .map(UserRole::getRole)
    .distinct()
    .toList();
```

그리고 두 필터의 쿼리는 이랬다.

| 필터 | 쿼리 | `userRoleList` |
|---|---|---|
| 권한 필터 (원래 자기가 쓰던 것) | `findUserWithRoleByUsername` | fetch join 됨 |
| 인증 필터 (넘겨준 쪽) | `findByDelYnFalseAndUsername` | **없음** |

- 권한 필터는 원래 **역할을 fetch join 한 쿼리**로 직접 조회했다. 그래서 `getUserRoleList()`가 동작했다
- 재조회를 없애면서 받게 된 객체는 **역할이 로딩되지 않은** 사용자다
- 필터 체인은 트랜잭션·영속성 컨텍스트 밖이라, 그 시점에 역할 목록을 채울 방법이 없다

3분도 안 돼 드러났고(2분 52초), 인증 필터의 쿼리를 권한 필터가 쓰던 것으로 올려서 고쳤다.

```java
-User user = userRepository.findByDelYnFalseAndUsername(username)
+User user = userRepository.findUserWithRoleByUsername(username)
     .orElseThrow();
```

**엔티티를 넘겨줄 때 공유되는 건 참조지 로딩 상태가 아니다.** "같은 User"라도 어떤 쿼리로 가져왔는지가 계약의 일부인데, 나는 그 계약을 확인하지 않고 공급자만 바꿔치웠다.

## ④ 캐시를 붙였다

③에서 쿼리를 무겁게 만들었으니(fetch join 3개), 이제 그 쿼리를 아예 안 부르게 했다.

```java
User user = userAuthCache.computeIfAbsent(username,
    k -> userRepository.findUserWithRoleByUsername(k).orElseThrow());
```

메뉴 권한 목록에도 같은 방식을 적용했다. `computeIfAbsent`는 키가 없을 때만 람다를 실행하므로, 사용자당 최초 1회만 DB를 친다.

## 이 코드에 지금 남아 있는 빚

29분은 여기서 끝났고, 캐시는 그대로 남아 있다. 다시 읽어보면 문제가 명확하다.

**TTL도 크기 제한도 없다.**

```java
@Bean
public ConcurrentHashMap<String, User> userAuthCache() {
    return new ConcurrentHashMap<>();
}
```

`ConcurrentHashMap`은 자바 표준 해시맵이다. 만료도, 최대 크기도, 축출도 없다 — 타입 선언 자체가 근거다. 사용자 수만큼 쌓이고 절대 줄지 않는다.

**권한을 바꿔도 반영되지 않는다.**

- 캐시에서 지우는 코드는 전체에서 **딱 한 곳**, 사용자가 INACTIVE일 때뿐이다
- 메뉴 권한 캐시에는 지우는 코드가 **아예 없다**
- 즉 관리자가 권한을 회수해도, 그 사용자의 캐시가 살아있는 한 계속 통과한다. 재시작 전까지

방향이 나쁜 쪽이라는 게 문제다. **권한 확대가 안 되는 건 "왜 안 보이지" 하는 UX 문제로 끝나지만, 권한 회수가 안 되는 건 보안 문제다.**

**인스턴스를 늘리면 더 나빠진다.** 인메모리 맵이라 서버마다 다른 스냅샷을 들고 있게 된다.

## 남는 교훈

**최적화는 대체로 무언가를 공유하는 일이고, 공유에는 계약이 따른다.**

- ③에서 공유한 건 엔티티였는데, 실제 계약은 "어떤 연관관계까지 로딩됐는가"였다
- 이건 타입으로 표현되지 않는다. `User`는 `User`일 뿐, 역할이 채워졌는지는 시그니처에 안 나온다
- 그래서 컴파일러가 안 잡아주고, 3분 뒤 사람이 잡았다

**빠른 연속 커밋은 정직한 기록이다.**

- 20:24에 최적화하고 20:27에 그걸 고친 이력이 남아 있다. squash 했으면 사라졌을 것이다
- 지금 이 글을 쓸 수 있는 이유가 그 커밋이 남아서다
- "깔끔한 히스토리"가 항상 좋은 건 아니다 — 시도와 실패의 간격 자체가 정보다

**성능을 위해 만든 것은 정합성 부채를 남긴다. 그 빚을 코드가 아니라 기억에 적으면 잊는다.**

- 캐시에 TTL을 안 넣은 건 당시엔 의도적인 선택이었을 수 있다(사용자 수가 적고, 부하 테스트가 급했다)
- 문제는 그 선택의 조건("사용자 수가 적을 때만 유효")이 코드 어디에도 안 적혀 있다는 것이다
- 지금 이 글이 그 기록을 대신하고 있지만, 원래는 주석이나 이슈가 했어야 할 일이다

**측정했으면 증거를 남긴다.** 부하 테스트를 돌렸는데 결과를 gitignore 하면, 3개월 뒤엔 "TPS 100"이라는 커밋 제목 하나만 남는다. 그 숫자는 인용할 수 없는 숫자가 된다.

# 전은성

레거시 개선, 성능 문제, 데이터 모델 전환처럼 **이미 돌아가는 시스템을 고치는 일**을 주로 해왔습니다.
백엔드가 중심이지만 같은 기능의 프론트엔드까지 함께 바꾸는 경우가 많았습니다.

이 페이지의 각 항목은 [블로그 글](/)에 과정이 남아 있습니다. 결론만 적고, 근거는 글로 링크합니다.

## 기술 스택

실제로 문제를 겪고 판단을 내린 것만 적었습니다. 학습만 한 것은 뺐습니다.

| 구분 | 스택 |
|---|---|
| 백엔드 | Spring · Spring Security · JPA/Hibernate · QueryDSL · MyBatis |
| 데이터베이스 | PostgreSQL · MySQL |
| 프론트엔드 | React · Next.js · TanStack Query · RTK Query |
| 인프라 | Kubernetes · Docker · 배포 자동화(셸) |
| 그 외 | Python |

## 프로젝트

### 1. 탄소배출 산정 B2B 웹앱

> MySQL · JPA/QueryDSL · Gradle 멀티모듈 · React

제품 단위 탄소배출량을 산정하는 B2B 서비스입니다. 스키마 관리, 조회 성능, 누적된 이중 구조를
차례로 정리했습니다.

**스키마 관리 — 도입한 도구를 3주 만에 걷어낸 판단**

Flyway를 도입했지만 베이스라인·모듈 인터리브·collation·FK 이름 네 가지가 연달아 걸렸습니다.
결정적이었던 건 *기존 DB에서는 무사한데 새 DB에서만 실패한다*는 사실이었습니다. 마이그레이션
도구의 핵심 가치가 재현성인데 그게 이미 깨진 상태에서 유지 비용만 남는 구조였습니다.

- 고려한 대안: 예외 케이스를 계속 커스텀 로직으로 흡수 → **기각**. 설정 클래스가 221줄까지
  자란 시점이 이미 신호였습니다
- 결과: 철수하고 필요한 부분만 자동화로 대체. 되돌아보면 커스텀 로직이 붙기 시작한 때가
  판단 시점이었습니다
- [Flyway를 도입하고 3주 만에 걷어낸 이야기](/AI/DB-Query/flyway를-도입하고-3주-만에-걷어낸-이야기.html) ·
  [ddl-auto의 빈틈을 보완 DDL 자동화로 메우기](/AI/DB-Query/ddl-auto-update의-빈틈을-보완-ddl-자동화로-메우기.html)

**조회 성능 — 읽기 비용을 쓰기 시점으로 옮기기**

5중 CTE 뷰가 조회마다 재계산되고 있었습니다. 물질화 테이블로 옮기되 섀도우·전환 2단계로
무중단 롤아웃했습니다. 갱신 지점을 기존 캐시 무효화 지점(3곳)만 믿지 않고 전수조사한 결과
가장 빈번한 경로가 빠져 있었습니다.

- [뷰를 물질화 테이블로](/AI/DB-Query/뷰를-물질화-테이블로-읽기-비용을-쓰기-시점으로-옮기기.html) ·
  [N+1 제거 4종 세트](/AI/Backend/n+1-제거-4종-세트-fetch-join이-답이-아닐-때.html) ·
  [PDF 다운로드 7초의 범인](/AI/Frontend/한글-폰트-pdf-성능.html)

**기술 부채 — 같은 버그를 두 번 고친 날**

V1/V2 이중 스택이 남아 있어 한 버그를 양쪽에서 고쳐야 했습니다. 단계를 나눠 통합하며
2,389줄을 삭제했습니다. 도달 불가능한 파일 102개도 함께 정리했는데, 죽은 코드가 더 최신이라
판단 근거를 오염시키던 상태였습니다.

- [같은 버그를 두 번 고친 날](/AI/Frontend/v1-v2-이중-스택-정리.html) ·
  [죽은 파일이 살아있는 파일보다 최신이었다](/AI/Frontend/죽은-파일이-더-최신이었다.html)

### 2. 블록체인 관리 플랫폼

> Hyperledger Fabric/Besu · Kubernetes · Next.js · 폐쇄망

웹에서 버튼을 눌러 블록체인 네트워크를 Kubernetes에 배포하는 플랫폼입니다. 관리자·사용자
포털 두 벌이 같은 백엔드를 공유합니다.

**한 건이 아니라 버그 클래스를 제거**

SFTP 디렉터리 생성에서 TOCTOU(확인과 사용 사이에 상태가 바뀌는 문제)가 발생했습니다. 예외로
감싸는 대신 명령 자체에 위임해 틈을 없앴습니다(35줄 → 20줄). 이어서 "같은 형태가 또 어디
있나"를 물어 상위 계층에서 동일 클래스를 찾았습니다.

- 고려한 대안: 낙관적 재시도 / 비관적 락 → **기각**. 셋의 선택 기준을 정리해두고 이 경우엔
  원자적 위임이 맞다고 판단했습니다
- [TOCTOU 한 건을 고치는 대신 버그 클래스를 없앴다](/AI/Backend/toctou-버그-클래스-제거.html)

**오픈소스 오퍼레이터 버그 우회**

사용 중인 오퍼레이터의 버그를 만났습니다. 포크 / 다운그레이드 / CRD 스키마 패치 세 가지를
비교했고, 폐쇄망이라 커스텀 이미지 파이프라인 부담이 크다는 점과 업스트림 리베이스가 영구
비용이 된다는 점 때문에 스키마 패치를 택했습니다. 우회 조치에는 버전과 증상을 주석으로
남겼습니다.

- [오퍼레이터 버그를 CRD 스키마 패치로 우회하기](/AI/Infra/오퍼레이터-버그를-crd-스키마-패치로-우회하기.html) ·
  [kubectl exec은 왜 멈추는가](/AI/Infra/kubectl-exec-타임아웃과-재시도.html)

**폐쇄망·장애 상황의 프론트엔드**

게이트웨이 장애 시 사용자의 F5 연타가 폭주로 이어지는 것을 sessionStorage 기반 서킷
브레이커로 끊었습니다. HTTP 환경이라 `navigator.clipboard`가 동작하지 않는 문제도 폴백으로
해결했습니다.

- [게이트웨이가 죽었는데 사용자가 F5를 누른다](/AI/Frontend/브라우저-서킷-브레이커.html) ·
  [로그아웃은 토큰만 지우는 게 아니다](/AI/Frontend/로그아웃은-토큰만-지우는게-아니다.html)

### 3. 장비 관리 시스템 (레거시 개선)

> PostgreSQL · MyBatis · Spring · JSP

JSP와 바닐라 JS로 짜인 화면 수십 개가 있는 시스템입니다. 권한 모델과 조회 성능을
개선했습니다.

**표현할 수 없는 상태 때문에 한 역정규화**

장비의 소속 조직을 두 단계 조인으로 유도하고 있었는데, "고객과 다른 조직에 속한 장비"를
모델이 표현할 수 없었습니다. 역정규화는 보통 성능 때문에 하지만 이번엔 표현력 문제였고,
그래서 캐시나 뷰 같은 다른 선택지가 애초에 답이 아니었습니다.

- 판단의 핵심: 백필을 *기존 조인 경로 그대로* 작성해, 신구 경로가 같은 답을 내는 구간을
  만들었습니다. 그 안에서는 쿼리를 아무 순서로 갈아끼워도 화면이 깨지지 않습니다
- [정규화된 조인을 버리고 역정규화하기](/AI/DB-Query/정규화된-조인을-버리고-역정규화하기.html)

**인덱스를 만든 날과 쓰인 날이 13일 떨어져 있던 이유**

GIN trigram 인덱스를 만들었는데 실행 계획에 안 나타났습니다. 원인은 쿼리가 컬럼을
`LOWER()`로 감싸고 있어 인덱스 표현식과 달라진 것이었습니다. 인덱스를 다시 만드는 대신
쿼리를 인덱스에 맞추는 쪽(130개소 `ILIKE` 전환)을 택했습니다.

- 덤으로 얻은 것: 제조사 검색을 드롭다운으로 바꾸니 부분일치 자체가 필요 없어졌습니다.
  가장 빠른 부분일치 검색은 부분일치를 하지 않는 것입니다
- [GIN trigram 인덱스를 만들었는데 왜 안 빨라지지?](/AI/DB-Query/gin-trigram-인덱스가-안-먹던-이유.html) ·
  [인증 필터가 매 요청 DB를 네 번 때리고 있었다](/AI/Backend/인증-필터가-매-요청-db를-네번-때렸다.html)

**방어 코드가 감추고 있던 버그**

조직 트리 탐색에 `depth < 10` 제한이 있었습니다. 무한 루프를 막는 코드처럼 보였지만, 실제로는
순환 참조라는 진짜 원인을 가리고 있었습니다. 순환 검출과 깊이 제약을 분리했습니다.

- [depth < 10 방어 코드가 버그를 감추고 있었다](/AI/Backend/depth-10-방어-코드가-버그를-감추고-있었다.html)

### 4. 자동매매 시스템 <small>(개인 프로젝트)</small>

> Python · 증권사 API · Docker Compose · 실계좌 운용

주식 자동매매를 직접 만들어 실계좌로 운용하고 있습니다. 돈이 걸려 있어 "맞게 생겼는지"와
"실제로 그런지"를 구분하는 습관이 여기서 나왔습니다.

**체결 47건을 역산해서야 드러난 수수료 오차**

화면 표시가 이상하다는 것에서 출발해 실제 체결 내역을 역산했더니 요율 자체가 틀려
있었습니다. 원인이 세 개였고 각각 성격이 달랐습니다 — 상수 미갱신, 세법 개정 누락,
참조 데이터 소스 자체의 오염.

- ETF 판별을 종목명 접두어에서 API 필드로 바꿨고, 판별 실패 시 과세 쪽으로 fallback하게
  했습니다. 손익을 실제보다 크게 보이는 쪽이 더 위험하다고 봤습니다
- 결과: 세금 계산 상대오차 1.250% → 0.068%
- [체결 47건을 역산해서야 드러난 수수료 오차](/AI/AI-Pairing/수수료율-4배-오차.html)

**켜는 게 맞나 — 3방향으로 검증하고 전부 기각**

ML 기능의 설정 버그를 고친 뒤, "그럼 이걸 켜는 게 맞나"를 별도 질문으로 분리했습니다.
A/B 백테스트 → 분류 타깃 3종 → 회귀+IC 세 방향으로 검증했고 **전부 기각**했습니다.

- 처음 쓴 교차검증에서 유의미해 보이는 값이 나왔지만 믿지 않고 walk-forward로 재측정한 결과
  0과 구분되지 않았습니다. 검증 방식 자체의 낙관 편향이었습니다
- [설정 버그를 고쳤더니, 그다음엔 'ML을 켜는 게 맞나'](/AI/AI-Pairing/ML을-껐다-켜봤더니.html) ·

## 일하는 방식

AI 페어링을 실무에 쓰고 있습니다. 도구 자랑이 아니라 **검증 장치를 어디에 두느냐**의 문제로
다루고 있습니다.

- 스펙을 쓰게 하고 **컨텍스트를 끊은 뒤** 자기검토를 시킵니다. 같은 세션에서 물으면 대체로
  "문제 없다"는 답이 옵니다
- 병렬 에이전트로 메모리 누수 51건을 찾았지만 그대로 믿지 않고 검증 게이트를 거쳐 49건만
  적용했습니다. 1건은 데이터 유실 위험이 있어 보류했습니다
- 실패도 적었습니다 — AI가 쓴 커밋 메시지가 실제 diff와 달랐던 일이 있습니다

[AI에게 스펙을 쓰게 하고 자기검토를 시키고](/AI/AI-Pairing/ai에게-스펙을-쓰게-하고-자기검토를-시키고-구현하기.html) ·

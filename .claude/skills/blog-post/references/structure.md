# 글의 골격

두 계열의 섹션 배치. 근거가 된 글을 각 항목에 적어뒀다 — 규칙이 의심스러우면 원문을 연다.
계열별 글 수는 `## 남는 교훈` 57편 / `## 정리` 35편 (140편 중, 2026-09-18 실측).

## 경험담

가장 많이 쓰는 계열이다. 뼈대는 넷이고, 가운데 두 개가 여러 섹션으로 늘어난다.

```
## 문제: <증상을 한 줄로>          ← 상황 불릿 3~4개로 시작
## <1차 시도 / 막힌 지점>           ← 여러 섹션이 될 수 있다
## 어떻게 고쳤나                    ← ### 로 나눠도 된다
## 남는 교훈                        ← 반드시 이 제목
```

### 여는 섹션의 두 가지 형태

**(a) `## 문제:` 로 바로 들어가기** — `toctou-버그-클래스-제거`, `캐시를-고쳤는데-안-빨라졌다`

첫 블록이 상황 요약 불릿이다. 무엇을 하는 시스템인지, 증상이 무엇인지,
주어진 정보가 무엇인지.

```markdown
## 문제: SFTP 업로드가 동시에 들어오면 터졌다

- 프로젝트: 웹 버튼 클릭 → Hyperledger Fabric·Besu 네트워크를 Kubernetes 클러스터에 배포하는 플랫폼
- 인프라 계층: JSch로 원격 서버에 SSH/SFTP 접속 → bash 스크립트 전송 후 실행
```

**(b) 훅이 되는 사실 하나로 열기** — `gin-trigram-인덱스가-안-먹던-이유`

제목 대신 사실 자체가 후킹일 때 쓴다. 이 경우 `## 문제` 는 두 번째 섹션이 된다.

```markdown
## 인덱스를 만든 날과 인덱스가 실제로 쓰인 날이 13일 떨어져 있다

- 2026-03-12 — GIN trigram 인덱스 추가
- 2026-03-25 — 인덱스가 쿼리 플랜에 처음 등장
- 그 사이 13일 동안 인덱스는 디스크만 차지
- 이 글의 주제 — 그 13일
```

### 시간순 변형

장애 복구처럼 시간이 논지일 때는 H2 를 타임스탬프로 쓴다 — `배포-파이프라인-연쇄-장애`.

```
## 09:41 — 배포하자마자 터졌다
## 10:12 — 1차 원인: 토큰이 서버에 없었다
## 10:18 — 2차 원인: 서버가 macOS였다
## 10:36 — 문제를 다시 정의했다
## 최종적으로 무엇이 바뀌었나
## 남는 교훈
```

### 넣으면 글이 강해지는 섹션

**틀린 시도를 남긴다.** 이 블로그 경험담의 핵심이다. 바로 정답으로 가지 않는다.

- `캐시를-고쳤는데-안-빨라졌다` — `## 1차 대응: 캐시와 병렬화` 다음에
  `## 왜 안 빨라졌나: 고친 곳이 병목이 아니었다`
- `gin-trigram` — `## 1차 시도: pg_trgm + GIN 인덱스` 다음에 `## 그런데 안 빨라졌다`

**선택지를 표로 비교한다.** 왜 이걸 골랐는지가 표 한 장으로 끝난다.

- `toctou` 의 `## 세 가지 도구의 선택 기준` — 방식 / 쓸 때 / 비용 3열
- `gin-trigram` 의 표현식 인덱스 vs 쿼리 수정 — 방법 / 내용 / 판단 3열

**남겨둔 것을 밝힌다.** `## 남겨둔 것` 또는 마지막 섹션 안에서.
무엇을, 왜 이번 범위가 아닌지, 제대로 된 해법은 무엇인지.
근거 — `캐시를-고쳤는데-안-빨라졌다` 의 `## 남겨둔 것`:
"고칠 수 있는 것과 이번에 고칠 것은 다르다."

### `## 남는 교훈` 의 형태

두 형태가 있다.

**(a) 굵은 문장 + 불릿** — `toctou`. 교훈이 여러 개일 때.

```markdown
**버그 하나를 고칠 때 "이 버그의 클래스가 뭔가"를 먼저 묻는 게 이득일 때가 있다.**

- SFTP 한 건에 예외 처리 덧대기: 5분 소요
- 대신 던진 질문 — "check-then-act 패턴이 어디에 또 있나"
```

**(b) 표로 시간 순서를 보여주고 서술** — `캐시를-고쳤는데-안-빨라졌다`.
무엇에 시간을 썼고 무엇이 헛수고였는지가 논지일 때.

어느 쪽이든 마지막은 **지금은 어떻게 하는가**로 닫는다. 다짐이 아니라 절차로.

## 정리·비교

```
## 왜 필요한가  또는  ## 결론부터     ← 둘 중 하나로 연다
## <개념 분해 — 여러 섹션>
## 그럼 <기존 방식> 은 이제 안 쓰나   ← 반박 섹션
## <한계 · 주의점>
## 정리                              ← 반드시 이 제목
```

### 반박 섹션을 반드시 넣는다

새 도구를 소개할 때 기존 것을 안 쓰게 되는 건 아니라는 점을 짚는다.
한쪽만 칭찬하는 글이 되지 않게 막는 장치다.

- `graphql-basic` — `## 그럼 REST 는 이제 안 쓰나`
- `messaging-basic` — `## 그럼 동기 호출은 이제 안 쓰나`

### 비교 글은 결론부터

`mermaid-vs-archify` 는 `## 결론부터` 로 열고 `## 그래서 언제 뭘 쓰나` 로 좁힌 뒤
`## 정리` 로 닫는다. 비교 글에서 결론을 뒤로 미루면 안 읽힌다.

## 제목

`CLAUDE.md` 의 블로그 원칙 — **제목으로 클릭을 유발한다. 면접관이 "이게 뭐지?" 하고 눌러야 한다.**

실측(2026년 글 105편): 길이 중앙값 **34자**, 범위 9~56자.
**46편(46%)이 em-dash(`—`)로 두 토막을 잇는다.**

가장 많이 쓰는 형태는 `<훅> — <구체적 사실>` 이다.

```
SSH 로는 되는데 Herdr 만 못 찾는다 — .zshrc 가 아니라 .zshenv 였던 이유
pull 은 됐는데 설정이 반만 적용된다 — 맥 4대 dotfiles 를 무인 동기화하기
북마클릿은 아직 죽지 않았다 — 무엇이 막히고 무엇이 되는지 직접 재봤다
```

em-dash 없이 문장 하나로 가도 된다. 이때도 **결과나 반전을 제목에 넣는다.**

```
캐시를 고쳤는데 안 빨라졌다
TOCTOU 한 건을 고치는 대신 버그 클래스를 없앴다
초당 85줄 로그가 그날의 매도 체결 기록을 지웠다
```

쓰지 않는 형태 — 주제만 적은 명사구. 누를 이유가 없다.

```
(X) 쿼리 성능 최적화기
(X) Spring 동시성 처리 방법
(X) 블로그 글쓰기 에이전트 구축기
```

## H2 작성 규칙

**명사구가 아니라 문장으로 쓴다.** 이 블로그 H2 의 가장 뚜렷한 특징이다.

| 쓰지 않는다 | 쓴다 | 출처 |
|---|---|---|
| 인덱스 최적화 | 그런데 안 빨라졌다 | gin-trigram |
| 원인 분석 | 왜 안 빨라졌나: 고친 곳이 병목이 아니었다 | 캐시를-고쳤는데 |
| 로깅 개선 | 원인 조사를 방해한 두 번째 결함 | toctou |
| 해결 방안 | 어떻게 고쳤나 | 공통 |

콜론을 써서 `<분류>: <내용>` 으로 쓰는 것도 흔하다 — `## 문제: SFTP 업로드가 동시에 들어오면 터졌다`.
